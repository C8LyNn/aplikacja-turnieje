## 2. Exact candidate column migration (PROPOSED SQL ONLY; DO NOT EXECUTE)

**Preferred durable storage:** `public.tournaments.basket_config_revision bigint` with one per-tournament monotonic server-owned counter, rather than a time-derived token, stage version-vector or ephemeral memory cache. Every transition that changes either the basket graph OR its relevant stage/roster dependencies must monotonically invalidate the previous ETag. Values are **opaque to the HTTP client** and need not increment by exactly one in a multi-statement transaction; only strictly increasing, never ABA is the safety requirement. If A110/owner demands exactly one numeric increment per logical full PUT, a separate idempotent per-transaction touch design must be independently reviewed; don't claim row triggers provide exactly +1.

The following is the **exact proposed base DDL shape** for future owner-reviewed migration (the real migration must also implement the trigger/privilege/compatibility provisions below). **NOT AN EXECUTABLE MIGRATION OR APPROVAL.**

~~~sql
-- PROPOSAL ONLY — NNNN_T055_BASKET_CONFIG_REVISION.sql (number NOT allocated).
ALTER TABLE public.tournaments
  ADD COLUMN basket_config_revision bigint NOT NULL DEFAULT 1;
ALTER TABLE public.tournaments
  ADD CONSTRAINT tournaments_basket_config_revision_positive
  CHECK (basket_config_revision > 0);
-- Drizzle schema counterpart: basketConfigRevision:
-- bigint("basket_config_revision", { mode: "number" }) is NOT safe beyond
-- JS Number.MAX_SAFE_INTEGER. Use mode:"bigint" and serialize as a decimal string.
-- No backfill from timestamp/stage.version/result_history.revision.
-- Monotonic revision owned by transactional database writer, not by HTTP body.
~~~

**Mandatory companion DB policy (not implemented):**

1. Add SQL `BEFORE UPDATE` guard on `tournaments` to **reject `NEW.basket_config_revision < OLD.basket_config_revision`** (including deliberate reset) and constrain unexpected direct UPDATE privileges; use an approved revision-touching DB function or a restricted dedicated ledger table if table-level application grants cannot protect server ownership. Require overflow to abort the transaction, never wrap.
2. Implement audited `AFTER INSERT/UPDATE/DELETE` invalidation/touch triggers **or equivalent formally exhaustive parent-first writer protocol** on `tournament_stages`, `players`, `stage_participants`, `stage_baskets`, `stage_basket_routes`, `stage_basket_participants`; include compatibility-sync triggers and any domain commands that change eligibility/roster/stage ordering. Trigger only relevant fields where demonstrably safe; conservative extra invalidation is acceptable, missed invalidation is not. Updates moving a record between tournaments must invalidate **both** old and new tournament IDs or be forbidden by FK/tenant constraints.
3. **Lock order:** all stage/roster/basket writers take the same `tournaments FOR UPDATE` lock for the target tournament **before** child locks/DML. A child-trigger revision bump does not by itself prevent a writer from locking children first and deadlocking with basket PUT. For legacy paths that cannot be brought into protocol, create a migration-backed fail-closed write boundary and document the actual lock graph before code GO. Serializable/deadlock retries must be bounded and testable, never silent last-write-wins.
4. Existing basket PUT updates stage derived counts/versions; stage-trigger invalidations can cause several numerical increments in **one** legitimate PUT. Expose only an opaque strong ETag based on the **final** committed revision. A110 acceptance should assert token **changes** and strictly increasing stored counter, not an unapproved requirement of exactly +1. Statement-level transition-table batching is an optional future optimization after source audit; don't claim tested.
5. No numeric sequence is portable between tournament identities; clone ID/authorization must be re-derived. Backfill existing tournament rows with a local baseline 1 and invalidate all old cards/clients by enabling `If-Match` only with coordinated API/Host/React cutover. Database default/backfill alone does not make old clients safe.
6. Before approving SQL, inventory **every** DML writer of six dependent tables across API/stage engine/qualification/routing/Backup restore/test fixture/legacy compat triggers, plus triggers with explicit `public.*`; independently review any `SECURITY DEFINER` `search_path`, tenant FK and privilege boundary. Unknown DML paths => **SQL_STOP**.

**Why ephemeral/vector alternatives fail D1:** short-lived token, current-timestamp, legacy `stage.version` (may reset/reuse across rebuild) or a digest of graph values can exhibit ABA when A→B→A, cannot cover roster changes reliably, and does not meet signed **persistent monotonic** requirement. **No fallback to those alternatives in R22.**

## 3. Atomic GET/PUT contract and transaction linearization (future source change)

**GET** `/tournaments/:id/stage-baskets`:
- Authorize tenant before read. One verified **READ ONLY REPEATABLE READ** transaction (driver-supported `accessMode:"read only"` / `isolationLevel:"repeatable read"`, must verify actual ORM contract in future code) loads row + revision + stages + players + basket graph + assignments from ONE MVCC snapshot. No ETag from a separate later SELECT.
- Emit one **strong** ETag in response header, e.g. `"sb-<tournamentId>-<opaqueRevision>"` generated only from this snapshot. Ensure route IDs and tenant identity cannot be used to authorize access; token is a precondition, not an access control. No cross-tenant reuse or weak `W/` token acceptance.

**PUT** `/tournaments/:id/stage-baskets`:
1. Authenticate organizer and actor; require precisely one valid, strong `If-Match` (missing -> **428**, malformed/multi-token/weak/`*` -> fail-closed **400 or 422**, NEVER write). Public/legacy clients with unconditional PUT need coordinated cutover before activation.
2. Begin single transaction; lock tournament parent `FOR UPDATE` before stages/roster/graph. Revalidate organizer/session/tenant mutation actor under lock. Parse expected ETag for **this tournament only**; load current DB revision **after parent lock**, compare to token **BEFORE all DELETE/INSERT/UPDATE**. If stale -> **412 `STAGE_BASKET_CONFIGURATION_STALE`**, full rollback/zero writes, no partial effects.
3. Under the same lock, query actual stage and roster invariants; assert row statuses/eligibility, compatibility revisions and actor policy. All approved other writers must have incremented revision under the same parent lock; a stale draft even if graph values match again (ABA) must fail. Missing required writer coverage, unexpected changed stage/roster or incompatible status -> STOP/412 with no mutation, not a stale-data silent merge.
4. Validate full requested graph; replace baskets/routes/assignments + stage computed fields and compiled routing plan within **this** transaction. DB guard/trigger bump(s) revision atomically with mutations, including changes in stage/roster. Publish **final** revision only after all trigger side effects, by re-selecting in transaction. On any SQL exception/revalidation failure, rollback **all** rows and revision.
5. Return new body + freshly generated strong ETag corresponding to the **committed logical graph**. If a concurrent writer commits after the transaction and before the HTTP response, the returned token may immediately be stale; that is safe (next PUT 412), not permission to silently retry.
6. React/Host editor on 412 retains draft within the same authorized tournament, requires explicit reload/reconciliation/user-confirmed save, never auto-replays stale If-Match. This is owned by A110/UI, not by A20.

**Invariant tests authored as oracle only (NOT_EXECUTED):** A and B GET V0 -> one PUT succeeds and yields different token; B's stale PUT 412 zero mutation, winner graph intact; stage/player/stage_participant update invalidates V0; insert-then-delete A→B→A remains invalid; no If-Match 428; malformed 4xx; unauthorized actor unchanged; trigger rollback restores old revision; parent-vs-child deadlock test; stage/roster edits crossing tournaments don't leak tokens; strict legacy client cutover.

Do not pretend a source-originated ETag remains valid post-clone or silently reject lawful historical backups. Strict importer must reject contradictory present history and malformed known IDs preclone, while genuine later DB errors require full transaction rollback (B2/B5/B6 decisions).
- Audit restore ordering: create new tournament, stage/roster graph, matches, history, action references in one transaction; dependency triggers may bump basket revision many times. Capture final clone-local basket revision after all inserts and trigger activity; never leak it before commit. Document if triggers fire through restore and if rollback fully reverts them.
