## 3. T055 persisted monotonic CAS: precise schema and transaction contract

Current release source:

Existing 409/422 errors are not signed 412/428.
- [PR #55 one integration-test-only file](https://github.com/C8LyNn/aplikacja-turnieje/blob/c3a4ea00ba933cbab36b3582859cb3eff20f0204/artifacts/api-server/test/stage-basket-cas.integration.test.ts), blob `f95f032f4146f33ccbba813a3d08b34dfb9bb929`, has CAS-01…CAS-10 negative/positive tests including 428, 412, concurrent editors, cross-tournament tokens, stage/roster drift. The tests **do not directly prove persisted monotonic BIGINT, A→B→A ABA, worst-case race barrier or frontend draft retention**; read-only QA plan must extend them.

**Required additive persisted design (not authorized SQL):**
- Preferred `tournaments.basket_config_revision BIGINT NOT NULL DEFAULT 1 CHECK (>0)`; Drizzle `bigint(...,{mode:"bigint"})`, never represent arbitrary 64-bit revision as a JS `number`. Serialize version as decimal text only inside a server-generated strong, quoted, tenant/instance-bound ETag; treat ETag as precondition, **not** authentication. A persisted distinct *generation/epoch* or equivalent identity is required if an application-level restore/recreate can reuse the same tournament ID and numerical revision (otherwise old ETags may be resurrected). For the existing clone-new-tournament restore flow, freshly allocated tournament ID and fresh local revision/generation avoid source-token reuse.
- A server-owned revision can **only strictly increase** in any committed relevant change; attempt to decrement, reset, overflow, spoof the HTTP body or advance via unauthorized writer must fail closed. Enforce ownership via narrow DB grants/trigger or dedicated mutator/guard and reviewed concurrent row-locking; a mere `CHECK >0` or "reject decrement" trigger is insufficient to guarantee increments on every relevant write. No in-memory token, `updated_at` timestamp, hash of graph values, `stage.version` vector or `xmin` substitute meets signed D1 and ABA coverage.
- Mutations to review for exhaustive revision invalidation: **`tournament_stages`**, **`players`**, **`stage_participants`**, **`stage_baskets`**, **`stage_basket_routes`**, **`stage_basket_participants`**, plus tournament state/authority, compatibility synchronization, qualification/routing outputs when they alter a draft's meaningful participants, restore/clone and import/admin paths. Only subset of columns truly relevant may be optimized *after* exhaustive writer audit. Move between tenants must bump both old/new or be forbidden. New fields/triggers must respect FK and permission boundaries.
- **Global lock order** for every relevant API writer: first `tournaments(id) FOR UPDATE`, then stages, then players/memberships, then baskets/routes/assignments, never child-first. Child trigger touches parent row may create parent/child lock inversion even though it ensures a bump; audit all legacy and trigger paths, establish bounded SQLSTATE deadlock handling, and do not silently retry a stale PUT.
- One read-only **REPEATABLE READ** GET transaction loads `basket_config_revision` and entire graph from one snapshot and produces **same-snapshot strong ETag**. Under the same parent lock a PUT revalidates the organizer/security actor and `If-Match` *before* DELETE/INSERT/UPDATE: missing -> **428**; malformed/foreign -> fail-closed 4xx/no writes; stale -> **412 `STAGE_BASKET_CONFIGURATION_STALE`** / zero writes. Recheck latest stage status and roster after lock. Legitimate PUT is one atomic graph+derived-stage+routing-plan+revision transaction; final revision may bump several times through child triggers, but must strictly advance and never repeat a committed historical token. Return its *final* token, no automatic stale retry; browser keeps local draft and demands explicit reconciliation (D6).
- Important nuance: **exactly +1 per full PUT is not guaranteed** when stage/child triggers also touch parent. Choose one transaction-scoped touch mechanism and tests around strict increase before any implementation GO. Migration also needs tenant-local privilege enforcement, exact lock graph and recovery from overflow without silent wrap.

**If not all relevant writers can be updated/guarded atomically, this design remains `DB_CONTRACT_BLOCKED`**. A token bound only to a graph hash is insufficient even if one CAS test passes.
