## 3. Trust model: Ed25519 / signers / canonicalization / expiry / replay

**Verified in source:** qa/web005/r23h-r5/signed-source-context.mjs lines 8–90 has hardcoded TRUSTED_ROLE_KEYS = Object.freeze({}); the three required role labels are A00, A20, OPERATOR. It canonicalizes JSON, insists on exactly three role entries, verifies Ed25519 signatures of identical base64-decoded canonical payload, rejects duplicate role labels, requires run_id, nonce, SHA-shaped plan/source/lock/config/kit/certificate claims, expiry within the upcoming hour, BASE DB/role OIDs, and fixed scope counts BASE+4, 36 integration tests and 2 forced pushes. The file path is hardcoded /run/web005/g4-context.json. With empty key map the function stops at TRUST_ROOTS_UNPROVISIONED **before it can authorize SQL**.

**Independent P0 limitations:** (a) a signature proves only possession of a private key matching pinned PEM, not that the real A00/A20/operator independently approved or observed anything; two role labels could be configured with the SAME public key, since no PEM/public-key fingerprint inequality check is present; (b) nonce and expiration fields are checked for shape/clock window but never atomically CONSUMED, so one signed payload could potentially be replayed during its validity; (c) source_sha is checked for 40 hex only, NOT compared to actual verified checkout/OCI image/tree, and the launcher remains inert rather than supplying measured source binding; (d) certificate hash and system_identifier are signed INPUTS, not observed live server state; (e) /run/web005/g4-context.json is read without file owner/mode/symlink/immutability custody check—although payload signature defeats unsigned changes, a valid old signed file can still be replayed without external CAS; (f) independent key custody, revocation, trust-anchor provenance, secure signer UI, time source and signature domain separation need separate A30/A00 approval. A second verifier in guarded-g4-launcher.mjs has another empty public-key map and different action name, thus this is **not one completed integrated production authority chain**.

**Mandatory design repair:** pin three cryptographically DISTINCT role public keys sourced via independently approved change; signed action must bind measured source SHA + image/lock/Compose/PGDATA/cluster context plus exact phase; verify issued_at/not_before/expiration and unique nonce at a durable external atomic compare-and-set service; observe independent physical target before any grant; reject same-key masquerading, forged/expired/replayed envelopes and changed working tree. Do not fill TRUSTED_ROLE_KEYS nor flip SOURCE_ONLY_LOCK under this audit.

## 4. Journal / custody / tampering

**Existing guarantee, qualified:** source-evidence-journal.mjs lines 17–37 writes a separately UUID-named event file with exclusive wx open, 0600 requested mode, write-loop, file fsync then directory fsync, and SHA256 receipt. verifyPersistedEvent rereads a file and compares its SHA against an IN-PROCESS receipt and selected expected fields. This is useful **crash-consistency and accidental corruption detection** within a cooperative process.

**It is not an append-only independently controlled journal.** The test process itself writes these files and keeps receipt hashes in memory, so a process/runtime able to manipulate files or its own memory could replace/truncate/delete events and receipts. Directory checkedDir() verifies only directory/not-symlink, not independently attested owner/mode/device/mount/inode, and receipt verification trusts path/hash and in-process expected values; there is no previous_event_hash monotonic chain, outside-process signature, no trusted server timestamp/statement receipt, no canonical cross-process event ordering or anti-rollback sequence. The partial read/write and fsync path can create orphan files on failure, and a tmpfs is volatile across restart. Directory/handle replacement and capacity exhaustion require future negative controls. Raw stderr is likewise source-controlled and can leak DSNs if downstream verbose tooling prints them; audit-only evidence cannot prevent SQL after the fact.

**Required:** independently owned append-only remote collector/server-side PostgreSQL DDL/event timeline, signed immutable run/slot sequence, trusted device/dir ownership provenance, tamper/cut/truncate/reorder/replay negatives, before/after OID/name/owner event reconciliation, secret redaction and custody SHA. Missing journal must block further destructive writes and create CLEANUP_HOLD; never infer server state from filesystem bytes alone.

## 6. Name collisions, TOCTOU, OID reuse and cluster spoofing

Before CREATE, the helper checks absent name; after CREATE it reads pg_database and stores exact DB OID/owner OID/current role; before DROP it compares fresh catalog with receipt. This blocks several common accidents including CREATE duplicate error, lost ACK and obvious changed owner/OID. It is **not linearizable**: a permitted second writer can rename/drop/recreate object after precheck before name-based DROP; an OID can be reused. Same-role attacks may preserve owner and role OID; cluster switch may even present coincidentally equal OIDs. A signature on a claimed system_identifier does not prove that a client actually connected to that system.

Required future evidence: controlled fresh PGDATA, no foreign writable actor or second SQL endpoint, independent G1 netns/volume/host/no-port/Windows witness, independently measured PG system_identifier tied to specific authenticated socket and G2 role/base IDs, freshness before sensitive G4 operations, plus safe failure injection for double writer, OID replacement and PG restart. Ideally add a mandatory server-side admission boundary/strong sole-writer enforcement, not a source-only string check. Physical no-touch of native Windows PG16 must be independently established. Neither same-run marker nor self-generated SHA ledger guarantees this property.
