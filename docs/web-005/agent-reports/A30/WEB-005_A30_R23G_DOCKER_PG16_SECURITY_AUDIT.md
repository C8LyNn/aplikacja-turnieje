## 1. P0 findings — BLOCKERS BEFORE ANY STATE CHANGE

### P0-01 — Conflicting Compose source of truth / host publication policy
**Evidence (CONFIRMED DESIGN CONFLICT):** [Drive Compose Option A](https://drive.google.com/file/d/1zLZsZ-APpSzgPwmSNsCJdU-4icwFC_jc/view) defines `pg16.network_mode:none`, `api-tests.network_mode:service:pg16`, private PG `127.0.0.1:55432`, and `ports: []`. A20 final handoff describes B host **55439**; Drive fallback uses **55432**. All files call themselves non-executable examples, but a dispatcher could choose the wrong one or mix them.
**Exploit/failure:** unintended Windows listener, broader Docker bridge topology and/or wrong PG instance; preflight claims "no host published ports" could pass against the **wrong** Compose file.
**Fix / verifier:** A00 must **sign exactly one topology** (A no host port recommended; B independent explicit exception), exact version+SHA256 of *one* canonical Compose/runner configuration, fixed internal/host port mapping and command mode, and explicitly **quarantine the unselected example**. Future operator read-only `docker compose config` offline and subsequent `docker inspect` on actual created IDs must corroborate `NetworkMode`, `HostConfig.PortBindings`, PG listener and absence of bridge/host network. Compare **actual** port against chosen signed record; any other port or secret file/path = FAIL. **Blocking:** G0/G1/G4.

### P0-02 — No physical database identity bound to code's destructive guards
**Evidence (SOURCE CONFIRMED + RUNTIME MISSING):** S1 guard validates database *name* containing "test", no "prod", schema regex and reset string. S2 validates loopback and `port != 5432` but never cluster system identifier or Docker volume/provenance. Host loopback/port/name/flags can all be spoofed or point to another local PG cluster.
**Exploit/failure:** `DROP SCHEMA ... CASCADE` or `DROP DATABASE ... WITH (FORCE)` on an existing unrelated database if the URL/namespace is wrong.
**Fix / verifier:** G1 create fresh cluster after proven no-preexisting volume and independent operator certificate (Docker host/context, image digest, container ID, PID/ns inode, PGDATA mountpoint, `pg_control` system ID). Require time-bounded run ID; invalidate certificate on restart/context drift. `pg_isready` is **liveness only**, not this attestation. **Blocking:** G2/G3/G4.

### P0-03 — S2 broad CREATEDB + forced database termination is not name-scoped

**Exploit/failure:** test role could create arbitrary DBs on a shared server; a mistaken target may erase owned DBs or forcibly terminate unrelated sessions.
**Fix / verifier:** allow S2 only in **physically isolated, disposable, independently certified empty PG16 cluster**, with single per-run non-superuser account, ownership/restriction inventory, `CREATEDB` only for brief authorized G3-S2/G4 window; no bootstrap superuser in runner. At G2 verify deny `rolsuper,rolcreaterole,rolreplication,rolbypassrls`, only expected base DB and templates, then operator attests role rights/DB list before and after; revoke `CREATEDB` or destroy owned cluster under G5. Fixture's exact three names must be logged post-generation; any unexpected name or database => STOP. **Blocking:** G3-S2/G4.

## 2. P1 findings — REQUIRES RESOLUTION BEFORE RELEVANT PHASE

### P1-01 — Bootstrap superuser secret persists as a runtime mount
**Evidence:** Drive Option A `pg16.secrets:pg_admin_password` with `POSTGRES_PASSWORD_FILE=/run/secrets/pg_admin_password`; Compose keeps secret file mounted for PG container lifetime, despite narrative "G1 bootstrap-only". The test runner does **not** mount admin secret — positive — but operator/daemon/PG-container privileged access may retrieve it beyond G1.
**Fix:** plan separate post-bootstrap container recreation without G1 secret mount, credential rotation/disable administrative login as compatible with documented recovery, or explicitly accept persistence in signed short-lived isolated-container threat model. Compare actual `docker inspect` mounts and secret-path availability after bootstrap without exposing bytes; test runner sees **only separate limited test secret**. **Verification:** admin secret absent from runner/container post-G1 where promised, role `NOSUPERUSER`, no raw password in inspect/log/Drive. **Gate:** G1→G4.

### P1-02 — No verified container security profile for PostgreSQL service
**Evidence:** Drive runner `read_only:true`, `no-new-privileges`, `cap_drop:ALL`, `tmpfs /tmp`; PostgreSQL service specifies no equivalent capability, rootfs, pid/memory/pids limit or seccomp customization. Docker Desktop daemon still privileged.
**Fix:** examine effective PG UID/GID and required bootstrap filesystem permissions, apply compatible least privileges and resource limits only after exact image compatibility QA; enforce no `privileged`, no host PID/IPC, no `docker.sock`, no hidden mounts or external Docker network. Runner container must be nonroot if compatible. **Verification:** inspect actual HostConfig capabilities/mounts/security, image process UID, network namespace and resource limits at G1, fail on privilege creep. **Gate:** G1/G2.

### P1-03 — Liveness and network-isolation claims need independent negative evidence
**Evidence:** `pg_isready` healthcheck probes the local listener but does not authenticate or prove image, cluster or SQL permissions. `network_mode:none` / `service:pg16` is **safe architecture at source**, not proof that deployed runner cannot reach Windows host, Docker gateway, LAN or Internet.
**Fix:** after phase GO verify exact network namespace and socket/listener, host-published binding table empty for Option A, no IPv6/portproxy side channel, and only private loopback PG endpoint accessible; make negative *non-mutating* connection probes to previously approved dummy endpoints where allowed, without contacting native Windows PG. **Verification:** signed inspect/proc/socket and read-only physical certificate, not a simple 200/pg_isready. **Gate:** G2.

### P1-04 — Secret and database evidence could leak through Google Drive
**Evidence:** A20 explicitly plans raw local stdout/stderr and only sanitized Drive reports; cloud folder is accessible to user but permissions can change; Python/TAP/pg errors can contain URLs, `PGPASSWORD`, env dumps, table rows or key-bearing Steam upstream URLs. The script executes child code inheriting `process.env`.
**Fix:** raw logs only in restricted nonsynced scratch; allowlist fields for cloud receipts, systematic redaction for libpq URLs, `password=...`, tokens, host metadata and potential fixture PII; **test redaction against synthetic canaries**, block upload on match. Commit only content SHA256 + sanitized artifact ID; never log `docker compose config` secret paths if revealing personal directories. Cloud Drive remote SHA rehash and ACL metadata review; Windows G: sync needs independent confirmation, not presumed. **Verification:** redacted Drive document contains zero synthetic canary markers and no secret-bearing DSN; compare correct SHA over *published sanitized bytes*. **Gate:** G4/G5.

### P1-05 — G4 fixture teardown happens before G5 and may fail halfway
**Evidence:** S1 test teardown automatically runs `DROP SCHEMA`; S2 `after()` automatically executes three `DROP DATABASE WITH (FORCE)` operations during G4, **not** after operator G5 permission. **Fix:** signed G3-S1/G3-S2 and G4 explicitly authorize *fixture-internal* matched-name cleanup as part of test execution; G5 permission covers **separate operator cleanup of remaining exact resource IDs**. On partial failure record all orphaned DB/schema names, preserve evidence, do not "fix" via blind DROP or automatic test retry. **Verification:** dry review of exact test hooks and success/failure path, operator before/after ownership inventory; any object outside run manifest ⇒ CLEANUP_HOLD. **Gate:** G3/G4/G5.
