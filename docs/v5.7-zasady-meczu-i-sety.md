# V5.7 — zasady meczu, mecze na sety i ochrona operacji

Etap V5.7 rozszerza silnik o **zasady rozstrzygania meczu** (wariant: mecz na sety) i domyka ochronę operacji
z V5.6 (start, przełożenie, termin, cofnięcie, anulowanie, zamiana, „Cofnij ostatnią akcję”).
Kolejne formaty turniejów, sezony i dywizje pozostają w planie — zob. `v5.7-silnik-kolejne-mozliwosci.md`.

## 1. Ochrona operacji (API)

Każda operacja zapisu sprawdza w API stan, który widział użytkownik. Zakres wersji jest dobrany tak, żeby
niezależne czynności się nie blokowały.

| Operacja | Co sprawdza API | Ponowienie tej samej operacji | Konflikt |
|---|---|---|---|
| Start, wstrzymanie, przełożenie, zmiana długości meczu | wersja meczu (`expectedRevision`, wymagana) | stan docelowy już jest → bez zmian, 200 | 409 `CONCURRENT_MODIFICATION` + aktualny stan |
| Wynik (także sety) | wersja meczu (jak w V5.6) | „Ten wynik był już zapisany” — bez drugiego zapisu | 409, wynik roboczy zostaje |
| Termin meczu | poprzedni termin (`expectedScheduledAt`) — **osobno od wersji wyniku** | ten sam termin → bez zmian | 409 `SCHEDULE_CHANGED` z aktualnym terminem |
| Cofnięcie / korekta wyniku | wersja meczu + zależności awansu | odrzucone (wynik jest już cofnięty) — nic nie cofa się drugi raz | 409 z nazwą meczu lub etapu |
| Anulowanie, przywrócenie, zamiana uczestników | wersja meczu | stan docelowy już jest → bez zmian | 409 |
| Cofnij ostatnią akcję | numer akcji, którą widział użytkownik (`expectedActionId`) | „Ta akcja była już cofnięta” | 409 `UNDO_ACTION_CHANGED` z nazwą obecnej akcji |

Termin i wynik mają osobne wersje: zmiana terminu przez drugą osobę nie unieważnia wpisanego wyniku i odwrotnie.
Zmiana samego stanu meczu (np. ktoś go rozpoczął) przenosi wynik roboczy na nową wersję z komunikatem
„Zapisz ponownie”; zmiana wyniku lub uczestników kończy się blokiem konfliktu z przyciskiem „Odśwież dane”.
Wynik roboczy (także sety) zostaje w karcie przeglądarki przy konflikcie, błędzie sieci, utracie odpowiedzi
i wygaśnięciu sesji.

**Cofnięcie i korekta a awans** (bez kaskad i bez cichego usuwania późniejszych wyników):

| Sytuacja | Wynik |
|---|---|
| Następny mecz (drabinka) jeszcze się nie rozpoczął | korekta dozwolona, zwycięzca w następnym meczu zostaje poprawiony |
| Następny mecz się rozpoczął lub ma wynik | blokada: „następny mecz (runda X, mecz Y) już się rozpoczął / ma wynik” |
| System szwajcarski: kolejna runda rozlosowana | blokada z numerem rundy |
| Awans z etapu zatwierdzony lub kolejny etap trwa / zakończony | blokada z nazwą etapu |
| Turniej zakończony | dozwolone tylko bez zależności (np. finał) — turniej wraca do stanu aktywnego spójnie |

## 2. Zasady meczu — trzy osobne rzeczy

* **Format rozgrywek** (drabinka, grupy, liga, szwajcarski…) — bez zmian.
* **Zasady wyniku meczu** (nowe, `match_rules` etapu): jedna gra, seria do N wygranych gier, jedna gra z remisem
  (liga), albo **mecz na sety**.
* **Punktacja tabeli** (punkty za zwycięstwo/remis/porażkę, kolejność rozstrzygania remisów) — bez zmian.

Brak `match_rules` = dotychczasowe znaczenie etapu (seria BO albo gra z remisem). Starsze turnieje nie dostają
wymyślonych setów.

### Mecz na sety
* Parametry: sety do wygrania (1–4), punkty w secie (11, 15, 21, 25; w planie etapów z pliku AI: 3–99), przewaga (1 albo 2).
  Te same zasady dla każdego seta.
* Przewaga 1: set kończy się dokładnie przy progu (np. 11:9). Przewaga 2: przy progu z przewagą 2 (11:9) albo
  po progu dokładnie wtedy, gdy przewaga osiągnie 2 (12:10, 15:13). Wynik 13:10 jest niemożliwy.
* Długość meczu wynika z setów (do 2 setów = najwyżej 3 sety); remisów nie ma.
* Gotowe ustawienia (nazwy opisują zasady, bez przypisania do dyscypliny): „Do 2 wygranych setów, set do 11,
  przewaga 2”, „Do 3 wygranych setów, set do 11, przewaga 2”, „Do 2 wygranych setów, set do 21, przewaga 2”,
  „Do 3 wygranych setów, set do 25, przewaga 2”.

### Jedno źródło zasad
Biblioteka `@workspace/match-rules` (używana przez API i interfejs) rozstrzyga: czy set jest poprawny
i zakończony, czy próg i przewaga są spełnione, czy mecz jest rozstrzygnięty, czy można dodać set i czy sety
zgadzają się z wynikiem meczu. **API decyduje** — odrzuca z konkretnym kodem i opisem:
`SETS_REQUIRED`, `SET_SCORE_IMPOSSIBLE`, `SET_NOT_FINISHED`, `SET_AFTER_MATCH_DECIDED`, `MATCH_NOT_DECIDED`,
`SET_TOTAL_MISMATCH`, `SETS_NOT_SUPPORTED`. Walkower i anulowanie nie mają setów.

### Tabele
Kolumny: punkty tabeli, mecze (W/R/P), **Sety** (wygrane:przegrane), **Małe pkt** (punkty w setach — informacyjnie)
i różnica setów. Kolejność rozstrzygania remisów się nie zmienia; w etapie na sety te same kryteria czytają się
jako „różnica setów” i „wygrane sety”. Małe punkty nie rozstrzygają miejsc.

### Zmiana zasad po starcie
Zasady meczu można zmienić tylko w etapie zaplanowanym (`PUT /tournaments/:id/stages/:stageId/match-rules`).
Po starcie etapu API odpowiada `MATCH_RULES_LOCKED`; nic nie jest przeliczane. Długości meczu w etapie na sety
nie da się zmienić osobno (`BEST_OF_FIXED_FOR_SETS`).

## 3. Interfejs
* **Kreator** (krok „Dopasuj”) i **tryb zaawansowany** (sekcja „Mecze”): wybór „Jak rozstrzyga się mecz”,
  jedno zdanie podsumowania, np. „Mecz do dwóch wygranych setów. Każdy set do 11 punktów, z przewagą dwóch.
  Zwycięstwo daje 3 punkty w tabeli.”, szczegóły pod „Dostosuj zasady”. Remisy wybiera się tutaj (sekcja tabeli
  ma już tylko punkty i terminy). Zakazane połączenia (sety + remisy, sety + inna długość meczu) API wyjaśnia słowami.
* **„Wybrany mecz”**: edytor setów (klawiatura, telefon, przyciski + i −), nazwy zawodników nad kolumnami,
  wynik w setach i małych punktach, opis braków („Do zwycięstwa brakuje: Rysie — 1 set, Wilki — 2 sety.”),
  zapis dopiero po rozstrzygnięciu. Mecze bez setów zachowują krótkie wpisywanie.
* Listy, „Ostatnie wyniki”, korekta, blok konfliktu, widok widzów i Stable pokazują sety; nagłówki mówią
  „do N wygranych setów” (Stable: „sety do N”). Stable edytuje sety tym samym edytorem.
* Powiadomienia mają motyw Experimental i znaczenie podane ikoną oraz etykietą dla czytników
  („Gotowe”, „Uwaga”, „Błąd”), nie tylko kolorem.
* Edytor setów reaguje na personalizację (gęstość, karty meczów, kształt, typografia).

## 5. Krótki przewodnik ręcznego sprawdzenia
1. Nowy turniej → odpowiedzi domyślne → „Dalej: dopasuj” → „Do 2 wygranych setów, set do 11, przewaga 2”.
   Sprawdź zdanie podsumowania; „Wstecz” i „Dalej” zachowują wybór. Utwórz turniej bez trybu zaawansowanego.
2. Dodaj uczestników, rozpocznij. W „Wybrany mecz”: „Wpisz pierwszy set”, 11:7 — widać „Sety 1:0” i czego brakuje;
   „Zapisz wynik” jest nieaktywny.
3. „Dodaj set 2”, wpisz 13:10 — komunikat o niemożliwym wyniku; popraw na 12:10 — „Mecz rozstrzygnięty”,
   nie można dodać seta 3. Zapisz — zielone powiadomienie „Wynik zapisany!”.
4. Zakładka „Tabela”: kolumny „Sety” i „Małe pkt”, notka o rozstrzyganiu remisów („różnica setów”).
5. „Popraw wynik” przy tym meczu → „Cofnij wynik i przejdź do wpisywania” → 11:7, 9:11, 11:9 → zapisz.
   Tabela się zmienia; historia wyników ma obie wersje.
6. Dwie karty przeglądarki z tym samym meczem: w obu wpisz różne sety, zapisz najpierw w pierwszej.
   Druga pokazuje „Wynik nie został zapisany” z aktualnym wynikiem i „Odśwież dane”; jej wynik roboczy zostaje.
7. Widok widzów i Stable (`/tournaments/:id`): te same wyniki i sety.
8. Personalizacja (np. „Futurystyczny e-sport”, „Minimalistyczny profesjonalny”): edytor setów zmienia wygląd.

## 6. Ograniczenia (świadome)
* Sety zapisuje się po zakończeniu meczu; trwający set istnieje tylko jako wynik roboczy w karcie przeglądarki
  (widz widzi wynik w setach dopiero po zapisie).
* Wszystkie sety mają te same zasady; brak innego seta decydującego, limitu punktów, wyjątków dyscyplin
  i dodatkowych modeli punktacji (np. 3–2–1–0) — są na liście kolejnych możliwości.
* Zasady meczu z kreatora obowiązują we wszystkich etapach turnieju; różne zasady per etap — przez plik AI
  albo zmianę zaplanowanego etapu przez API.
* Zmiana zasad po starcie etapu nie jest możliwa (brak procedury przeliczenia).
